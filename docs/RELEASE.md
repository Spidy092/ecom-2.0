# Grovia Build, CI and Release Plan

## 1. Release principle

Customer ZIPs must be generated by automation from a known commit/tag. Never assemble release packages manually from a developer laptop.

## 2. Branch model

Initial lightweight model:
- `main` — releasable/protected integration branch;
- short-lived `agent/*` / feature branches;
- pull request required for substantive changes once code work begins.

Avoid long-lived environment branches unless operational evidence requires them.

## 3. Pull-request checks

Introduce these as relevant code is added:

```text
PR
 -> PHP syntax
 -> PHPCS / WordPress Coding Standards
 -> PHP static analysis
 -> JS/CSS lint/build checks
 -> unit tests
 -> WordPress/WooCommerce integration tests
 -> dependency/secret checks
 -> package smoke test
 -> selected browser smoke tests
```

The pipeline should fail fast on cheap checks and run slower browser tests after the basic build is valid.

The current engineering-alpha workflow is `.github/workflows/engineering-alpha-php.yml`. It runs the
static contracts plus a real WordPress/WooCommerce/Chrome regression job for `main` and pull requests
targeting `main`. That job pins WordPress 7.1, WooCommerce 11.0.1 and PHP 8.3 from `.wp-env.json`,
prints the runtime versions, seeds deterministic HPOS-safe fixtures, and exercises Search/Cart, Saved,
department browse, delivery, mobile navigation, visual states and Buy Again. Static/unit green is not a
substitute for this installed storefront evidence.

### Engineering-alpha compatibility lanes

The engineering-alpha browser E2E lane is a **release-gating/reproducibility lane**. It must pin exact WordPress, WooCommerce and PHP versions in repository configuration and print those versions in CI before running shopper flows. A passing commit should therefore mean the same tested platform combination over time.

A future **latest/forward-compatibility lane** may intentionally follow the newest supported WordPress/WooCommerce releases, but it must be separately named and non-release-gating until the new platform versions are explicitly adopted into the supported compatibility matrix. Do not use `core: null` in the release-gating wp-env configuration.

## 4. Release candidate flow

```text
Merged main
 -> version decision
 -> changelog
 -> release tag (e.g. v0.1.0)
 -> clean checkout
 -> dependency install from lockfiles
 -> production build
 -> full validation
 -> create grovia.zip
 -> create grovia-core.zip
 -> generate checksums/manifest
 -> artifact inspection
 -> human release approval
 -> publish/update channel
```

## 5. Versioning

Use semantic versioning as the default communication model:
- PATCH — backwards-compatible fixes;
- MINOR — backwards-compatible features/meaningful improvements;
- MAJOR — breaking public behavior/API changes.

Pre-1.0 versions may evolve quickly, but avoid casual breaking changes to customer data or documented extension points.

## 6. Package validation

Automated package checks should verify:
- expected root folder names;
- required WordPress theme/plugin headers/files;
- no `.git` directory;
- no local `.env`/secret files;
- no development-only dependency trees unless required at runtime;
- no test fixtures containing secrets/customer data;
- no marketplace-incompatible junk files;
- third-party notices/licenses included when redistribution requires them;
- install/activation smoke test from the built ZIPs.

## 7. Compatibility matrix

Each supported release should record the versions tested for:
- WordPress;
- WooCommerce;
- PHP;
- browsers;
- selected mobile viewport/device classes.

Automate the most important combinations; use risk-based manual testing for combinations that are impractical in CI.

## 8. Release notes

Every customer release includes:
- version/date;
- user-visible additions;
- fixes;
- security fixes with appropriate disclosure timing;
- compatibility changes;
- deprecations/breaking changes;
- upgrade notes when needed.

Do not bury security-relevant upgrade guidance in generic prose.

## 9. Rollback and emergency release

Before public paid launch define:
- how a bad update is withdrawn;
- how the previous package is restored;
- how customers are notified;
- how an emergency patched release is built without bypassing essential security/build validation.

## 10. Automated demo/docs deployment

Later CI can deploy product docs/demo after protected-branch approval. Deployment automation must use scoped credentials and must not make production secrets available to untrusted pull-request code.

## 11. Supply chain

- Commit lockfiles.
- Minimize CI actions/dependencies.
- Pin third-party GitHub Actions to trusted versions/SHAs where appropriate.
- Review permission requirements.
- Default workflow permissions to the minimum required.
- Do not execute arbitrary fork PR code with privileged secrets.

## 12. Definition of release-ready V1

V1 public release requires:
- acceptance journey passing;
- supported compatibility matrix tested;
- no release-blocking security issues;
- deterministic installable packages;
- upgrade path tested from the previous published version/beta where applicable;
- documentation and support route live;
- license/third-party asset inventory complete;
- demo and checkout operational;
- release notes/changelog ready.
