# Grovia Build, CI and Release Plan

## 1. Release principle

Customer ZIPs must be generated by automation from a known commit/tag. Never assemble release packages manually from a developer laptop.

The executable package rules live in `docs/COMMERCIAL-PACKAGE-CONTRACT.md` and `tools/release/build_packages.py`.

## 2. Branch model

Initial lightweight model:
- `main` — releasable/protected integration branch;
- short-lived `agent/*` / feature branches;
- pull request required for substantive changes once code work begins.

Avoid long-lived environment branches unless operational evidence requires them.

## 3. Pull-request checks

Introduce these as relevant code is added:

```text
PR
 -> PHP syntax
 -> PHPCS / WordPress Coding Standards
 -> PHP static analysis
 -> JS/CSS lint/build checks
 -> unit tests
 -> WordPress/WooCommerce integration tests
 -> dependency/secret checks
 -> deterministic package build
 -> install/activation smoke from built ZIPs
 -> selected browser smoke tests
```

The pipeline should fail fast on cheap checks and run slower browser/package tests after the basic build is valid.

## 4. Release candidate flow

```text
Merged main
 -> version decision
 -> changelog
 -> release tag (e.g. v0.1.0)
 -> clean checkout
 -> dependency install from lockfiles
 -> production build
 -> full validation
 -> create Theme installable ZIP
 -> create Core installable ZIP
 -> generate SHA256SUMS + release-manifest.json
 -> install/activate the generated ZIPs in clean WordPress
 -> artifact inspection
 -> human release approval
 -> publish through selected commercial update/download channel
```

During engineering alpha the filenames remain `storefront-theme-<version>.zip` and `storefront-core-<version>.zip`. Final product/package slugs are a branding/release decision and must be changed deliberately rather than inferred from the internal codename.

Do not replace the canonical installable archives with an ambiguous `all-files.zip`. If a future convenience bundle exists, label it as not directly installable in WordPress and keep the Theme/Core ZIPs unchanged inside it.

## 5. Versioning

Use semantic versioning as the default communication model:
- PATCH — backwards-compatible fixes;
- MINOR — backwards-compatible features/meaningful improvements;
- MAJOR — breaking public behavior/API changes.

Pre-1.0 versions may evolve quickly, but avoid casual breaking changes to customer data or documented extension points.

Theme and Core are independently versioned artifacts under one customer purchase/entitlement. Release metadata records both versions, and any minimum cross-version dependency must be explicit before incompatible combinations are shipped.

## 6. Package validation

Automated package checks verify:
- expected single root folder per archive;
- required WordPress theme/plugin headers/files;
- valid `theme.json`;
- Core declares WooCommerce through `Requires Plugins`;
- Core header/constant versions agree;
- no `.git`/`.github` directory;
- no local `.env`/secret key/certificate files;
- no development-only dependency trees unless required at runtime;
- no `tests/`, caches or test fixtures in customer archives;
- no marketplace-incompatible junk files;
- SHA-256 checksums and machine-readable manifest are generated;
- building the same source twice in CI produces identical Theme/Core ZIP bytes;
- install/activation smoke succeeds from the generated ZIPs in a clean WordPress/WooCommerce environment.

Paid/public publication remains blocked until reviewed package `LICENSE` files and required third-party notices/assets are complete.

## 7. Compatibility matrix

Each supported release should record the versions tested for:
- WordPress;
- WooCommerce;
- PHP;
- browsers;
- selected mobile viewport/device classes;
- specifically advertised third-party plugin integrations.

Automate the most important combinations; use risk-based manual testing for combinations that are impractical in CI. Compatibility is a tested claim, not an assumption that every WordPress/WooCommerce plugin will work.

## 8. Release notes

Every customer release includes:
- version/date;
- Theme version and Core version;
- user-visible additions;
- fixes;
- security fixes with appropriate disclosure timing;
- compatibility changes;
- deprecations/breaking changes;
- upgrade notes when needed.

Do not bury security-relevant upgrade guidance in generic prose.

## 9. Rollback and emergency release

Before public paid launch define:
- how a bad update is withdrawn;
- how the previous Theme/Core package is restored;
- how customers are notified;
- how an emergency patched release is built without bypassing essential security/build validation.

Never hot-edit a published ZIP to create an emergency release; produce a new version from automation.

## 10. Automated demo/docs deployment

Later CI can deploy product docs/demo after protected-branch approval. Deployment automation must use scoped credentials and must not make production secrets available to untrusted pull-request code.

## 11. Supply chain

- Commit lockfiles.
- Minimize CI actions/dependencies.
- Pin third-party GitHub Actions to trusted versions/SHAs where appropriate.
- Review permission requirements.
- Default workflow permissions to the minimum required.
- Do not execute arbitrary fork PR code with privileged secrets.
- Seller API keys, webhook secrets, package-signing credentials and commercial-provider credentials must never be present in customer archives or untrusted PR jobs.

## 12. Definition of release-ready V1

V1 public release requires:
- acceptance journey passing;
- supported compatibility matrix tested;
- no release-blocking security issues;
- deterministic installable Theme/Core packages;
- built-ZIP install/activation smoke passing;
- upgrade path tested from the previous published version/beta where applicable;
- documentation and support route live;
- reviewed package licenses and third-party asset inventory complete;
- final product/package naming approved;
- demo and checkout operational;
- commercial download/update provider selected and lifecycle proven;
- release notes/changelog ready.
